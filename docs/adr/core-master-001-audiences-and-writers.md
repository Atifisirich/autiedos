# ADR core-master-001: read audiences, writers and portal visibility for core master data

Status: accepted (core master data stream, 2026-11-24). Builds on ADR 001–005 and `docs/platform-foundation.md`.

## Context

MAP-TABLES section B puts ~67 shared tables in `core`. The foundation offers one generator kind for them,
`app.apply_rls(..., 'core_master', product, module)`, whose read rule is "any member of the org with any product".
Guardian, parent and student users (ERP portal, decision 30) hold a product grant (`erp: portal`), so with that rule
alone a parent would read every student, staff row, health note and incident of the school.

## Decision

1. **One wrapper, `app.apply_core_rls(table, read, product, module, extra, guard)`.** It calls the foundation
   generator unchanged (writes, audit trigger) and replaces only the select policy with an audience rule:
   `members` (reference data), `staff`, `permission` (`<module>.view`, restricted data) or `self` (`user_id`).
   Portal and self-service rows are an explicit OR-ed predicate per table (own learners, own household, sections of
   own learners, own staff row, own requests); `guard` is AND-ed (CRM-only consent rows). Every read keeps the
   foundation bound `org_id = app.current_org_id() and app.user_has_any_product(org_id)`.
   Rejected: a new `kind` inside `app.apply_rls` — the foundation function is shared and its 5-argument call is
   already ambiguous next to the legacy OS overload; a separate wrapper keeps the foundation untouched.
2. **Writers.** `product = '*'` (any product with the module permission) by default, because B's default writer
   rule is "owning product when the org has it, else the next one" and only the product servers know which applies.
   Where B names a single writer with no fallback the policy names it (`os`: staff_attendance, leave_requests,
   leave_balances; `erp`: enrolments, student_leave_requests).
3. **Tenant safety by construction.** Every core table has `unique (org_id, id)`; every FK between org-scoped
   core tables is composite `(org_id, x) → (org_id, id)`; login links reference `core.org_users(org_id, user_id)`.
   A cross-org reference is impossible even for the table owner. The harness checks all three generically.
4. **Restricted data in separate tables.** Health and category fields live in `core.student_sensitive` (1:1),
   readable with `student_sensitive.view` or by the learner's own guardian. Incidents, consents, compliance,
   outbox and integrations require `<module>.view`.
5. **Student status** changes only through `core.change_student_status()` (security definer); a trigger refuses a
   direct status update by any request role (checked on `current_user`, not a session setting any role could set).
6. **Generated DDL.** Files 100002–100007 are generated by `scripts/gen-core-master.mjs` and committed, so the 67
   tables cannot drift from the standard columns, indexes, grants and RLS call.
7. **Portal helpers are plpgsql security definer** (`app.my_core_staff_id`, `app.my_household_ids`,
   `app.my_learner_section_ids`) with `search_path = ''`, created before the tables they read.

## Consequences

* A new core table must go through `app.apply_core_rls` and get fixture rows for org A and B, or the harness fails.
* Parent/student screens can read core tables directly (ERP Data API, decision 51) without leaking other families.
* Orgs without OS cannot write staff attendance/leave (and without ERP cannot write enrolments / learner leave)
  until the owner decides otherwise; changing a writer is a one-line spec change plus a new migration.
* Column-level write ownership between products on shared rows is still a server responsibility (MAP-TABLES risk D1).
