## 0. Rules applied to every row (not repeated per row)

| # | Rule | Applies to |
|---|---|---|
| R1 | `tenant_id` → `org_id uuid not null references core.organizations(id)` | all CRM tables |
| R2 | `year_id` (ERP, CRM) → `academic_year_id` (OS name) | ERP `year:true` tables, CRM `programmes`, `enquiries` |
| R3 | Standard columns on every table: `id uuid pk`, `org_id`, `branch_id` (where the source has it), `created_at`, `created_by uuid default auth.uid()`, `updated_at` (trigger), `deleted_at` (OS `app.standardize`, generalised to `app.standardize(schema, table)`) | all; ERP lacks `updated_at`/`deleted_at`, CRM lacks most |
| R4 | `created_by` / actor columns hold `auth.users.id`; CRM `users.id` values are remapped to the new auth user id | CRM |
| R5 | Free-text actor names (`*_by_name`, `actor_name`) stay as display snapshots but every one gets a real id column next to it (`*_user_id` or `*_staff_id`) | ERP |
| R6 | Person references: `staff_id → core.staff`, `student_id → core.students`, `household_id/guardian_id → core.*` (ERP); CRM people refs go to `crm.*` until admission (decision 38) | all |
| R7 | **core never has a foreign key into `os`/`crm`/`erp`.** Where a source column points into a product table it becomes `linked_type text + linked_id uuid` (no FK) or moves to a product-side 1:1 table | core |
| R8 | Product role ids are not referenced from core: core stores `role_key text` + `product_key` (see OQ-6) | positions, approvals, ticket categories, notification rules |
| R9 | File path / file name columns → `*_file_id uuid references core.files` (path kept only for migration) | all |
| R10 | Enum-like text values: lowercase snake_case words; mappings listed in section B | all |
| R11 | Every table: RLS generated by `app.apply_rls(schema, table, kind, product, module)`; product tables check `app.user_has_product(org_id, product)` | all |
| R12 | Anthropic removed (decision 40): any model id / provider value `anthropic`, `claude-*` → `gemini` / mock | OS `platform_settings`, `ai_generations`; ERP `src/lib/ai.ts` |

Action vocabulary: **keep** (same name, new schema) · **rename** (new name) · **merge into X** (rows/columns go into a canonical table whose base is another source) · **drop as duplicate** (feature owned by another product, rows not migrated) · **replace by core function** · **drop** (not needed on the platform).

## D. Risks

1. **Write ownership on shared rows.** core.students/staff/attendance get writes from two products; without field-set enforcement (column grants per server role or `core.*` write functions) one product can overwrite the other's fields. Mitigation: core tables writable only through `core.*` functions; column-level grants for direct ERP Data API access (decision 51).
2. **ERP Data API exception (decision 51)** means ERP RLS alone protects `core`; a missing product check on any core policy leaks OS/CRM data to ERP users. Isolation tests must cover every core table × product.
3. **OS code churn:** `class_id → programme_id`, `students.full_name`, `parent_phone`, `audit_log`, schema-qualified names across ≈220 routes and tests; high regression risk before Phase 3 sign-off.
4. **Identity collapse:** three auth models (OS Supabase OTP + own session, ERP Supabase email, CRM bcrypt + TOTP) merge into one; with decision 37 a CRM email already used in another org cannot be reused, and a guardian phone cannot exist in two client orgs (blocks shared-family cases across separate client groups).
5. **Duplicate families at admission:** matching by guardian phone can merge wrong households or create duplicates (CRM `mobile` unique per tenant; ERP had no unique). Needs a review queue in `core.admit_student`.
6. **Feature loss for single-product clients:** ERP-only clients lose ERP enquiries, staff tasks, lesson plans, trainings, appraisals, invigilation (now OS/CRM-owned); OS-only clients keep student attendance only through core rows. Product scope must state this.
7. **Enum/value mapping errors** (attendance codes, statuses, gender, relation, board, language) silently change meaning; mappings must be data-driven and tested with golden fixtures.
8. **Payments in two places:** admission/registration fees in crm.payments vs ERP receipts/vouchers; risk of double counting in accounts and two receipt series (OQ-16).
9. **Cross-schema references** (core → product) are forbidden (R7); `linked_type/linked_id` columns lose referential integrity and need orphan checks in jobs.
10. **Scale of ERP port** (186 tables, ~100 screens) on the same database; ERP generator conventions (`app.t`, `app.secure`, `app.org_id()`) must be rewritten to the platform helpers or two RLS dialects coexist.
11. **Count drift:** plan cites 128 OS tables, migrations contain 127; table catalogue must be generated from the database, not from documents.
